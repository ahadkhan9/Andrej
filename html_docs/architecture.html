02. Embeddings: Mapping to Vector Space

00. Overview → 01. BPE Parsing → 02. Embeddings → 03. Attention → 04. Pipelines → 05. Generation

The Token's Journey

Our token character ID 15496 ("Hello") has no semantic meaning or context of where it sits in the sequence. It's just a raw primary key.

  1. Token Lookup (wte): The index is used to fetch the 15,496th row of the Token Embedding weight matrix. This yields a dense feature vector of dimension [384].
  2. Position Lookup (wpe): Because attention calculations are position-blind, we fetch position index 0 (for the first token in the sequence) from the Position Embedding matrix, yielding another [384] vector.
  3. Summation: We add these two vectors together: x = tok_emb + pos_emb, producing a single tensor of shape [B, T, C].
flowchart TD ID["Token ID [15496]"] -->|wte lookup| WTE["tok_emb vector [384]"] Pos["Pos Index [0]"] -->|wpe lookup| WPE["pos_emb vector [384]"] WTE & WPE -->|Element-wise Sum| Summed["Output Vector [384]"]

Backend Engineer Lens: Index Lookups

In backend engineering, an embedding lookup is a standard **indexed primary key query** in an in-memory directory.

Think of wte as a database table of pre-computed floats of size [50257, 384]. When we query the table using the token ID, we retrieve a dense record representing the token's initial semantic values.

Since attention is completely order-independent (like a bag-of-words or database rows without sorting), we must inject ordering metadata. We do this by adding a secondary index record—the positional embedding vector `wpe`—directly to our semantic record.

Transitioning to Code

In PyTorch, nn.Embedding acts as a lookup wrapper around a learnable parameter matrix of size [num_embeddings, embedding_dim]. Under the hood, this is a fast row-index gather operation (comparable to `W[idx]`), not a matrix multiplication.

Production Relevance

  • Vector Databases: When building a RAG application, your vector search database (pgvector, Chroma, Milvus) index operates in this exact embedding vector space. User query embeddings are compared against document chunk embeddings using cosine similarity dot-products.
  • Shared Weights (Weight Tying): In GPT-2, we tie the weights of wte directly to the output projection head lm_head. This means the matrix mapping words to vectors is the exact same matrix mapping vectors back to words, reducing our model memory footprint by ~19M parameters!

Verification

We verify embedding shape behavior by checking the output size of the summed embeddings in `forward`: `tok_emb` of shape [4, 256, 384] and `pos_emb` of shape [256, 384] correctly sum to produce a [4, 256, 384] tensor due to PyTorch broadcast rules. All logit outputs match HF expectations to $10^{-5}$ precision.

Common Interview Followups

Why do we sum token and position embeddings instead of concatenating them?

Concatenating them would result in a larger vector dimension (e.g. $384 + 384 = 768$), which doubles the parameter count and computation cost of all subsequent linear projection layers. Summing keeps the dimension size at 384. Because our transformer blocks are composed of linear layers, the model can mathematically learn to project and separate the position information from semantic features internally, behaving identically to concatenation without the memory penalty.

What is the limitation of absolute positional embeddings (wpe) used in GPT-2 compared to Rotary Position Embeddings (RoPE)?

Absolute positional embeddings (used in GPT-2) learn a static index parameter for every step up to block_size (e.g. 0 to 1023). If you try to feed the model a context sequence of length 2048, it will crash because the position matrix lacks rows beyond index 1023. Rotary Position Embeddings (RoPE, used in Llama 3) apply a rotational transform to Query and Key vectors during the attention step. This calculates relative distances between tokens dynamically rather than absolute indexes, allowing context length extrapolation during serving.
