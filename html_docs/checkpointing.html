09. Checkpointing: Serialization & State Restoration

The Token's Journey

As training steps execute, the weights of all layers ($wte$, blocks, output head) are continuously modified by gradients. If our training process crashes, all learning states are lost. Every 20 steps, the model freezes execution, compiles its parameter states into a dictionary object, and writes a serialized checkpoint snapshot (checkpoint_step_N.pt) to local disk storage.

flowchart TD InMem["In-Memory Tensors (model + optimizer state)"] -->|torch.save dict| Disk[".pt Checkpoint file on disk"] Disk -->|torch.load map_location| Restore["Restored Tensors mapped to Device RAM"]

Backend Engineer Lens: Snapshots & Migrations

In backend engineering, checkpointing matches **application snapshot serialization and database backup restoration**.

  • Serialization → Redis Snapshot: A checkpoint dictionary maps parameter names (like database schema columns) to multi-dimensional float arrays. Saving this is identical to serializing an in-memory session cache to disk.
  • map_location → Target Environment Configuration: If you try to restore a database backup saved on a production Postgres instance directly to your local development host without mapping target parameters, connection configurations crash. Similarly, loading a checkpoint saved on GPU memory directly to a machine without a GPU will cause a crash unless you specify map_location=device to direct the tensors to the local host's CPU/MPS RAM.
  • Weight Transpositions → Schema Migrations: Hugging Face's official GPT-2 weights are saved in a custom Conv1D format that expects weights to be aligned as $X \cdot W$. PyTorch's standard `nn.Linear` expects weights to be $X \cdot W^T$. When loading pretrained weights, we must execute a data schema migration—applying a matrix transpose operation (weight.t()) to align the tables before copying them into memory.

The Code-to-Concept Map

Concept PyTorch Code Code Location Production Equivalent
Save Checkpoint torch.save(checkpoint, path) train.py: main() save block Redis backup dumps
Load Checkpoint torch.load(..., map_location=device) hellaswag.py: main() Database restore scripts
Weight Transpose sd[k].copy_(sd_hf[k].t()) model.py: from_pretrained() Data schema column migrations

Production Relevance

  • Model Registries: In enterprise ML pipelines, checkpoints are versioned and stored in Model Registries (such as Hugging Face Hub, MLflow, or Weights & Biases) to serve as release tags for staging and production serving environments.
  • Safetensors Format: PyTorch's default `.pt` checkpoint format uses Python's `pickle` library for serialization. Pickled files can execute arbitrary Python scripts on the host system during load, presenting a security vulnerability. Modern production pipelines enforce the use of **Safetensors** files, which only store raw tensor byte values, completely preventing Remote Code Execution (RCE) hazards.

Verification

We verify our checkpoint restoration by running text generation using pre-trained weights. If the transpositions were incorrect, the output logits would fail parity checks, and the model would generate gibberish characters. The parity check passes with negligible variance ($10^{-5}$):

python3 generate.py --run_test

Common Interview Followups

Why do we transpose Hugging Face's Conv1D weights when loading them into standard PyTorch Linear layers?

In standard PyTorch, an nn.Linear layer performs matrix multiplication using: $$Y = X \cdot W^T + b$$ Where $W$ is the weight matrix and $X$ is the input tensor. Hugging Face's original GPT-2 implementation used a custom Conv1D layer (which behaves like a linear layer but uses a different memory layout) that computed: $$Y = X \cdot W + b$$ Because the weight matrix $W$ in the Conv1D file is saved transposed relative to PyTorch's expectation, loading it directly causes a shape mismatch crash. We must transpose the matrix using .t() before loading: 

sd[k].copy_(sd_hf[k].t())

What is state_dict in PyTorch, and what does it contain?

A state_dict is a standard Python dictionary that maps each trainable layer parameter name (string) to its corresponding tensor weights. It only contains the learnable weights and biases of the model, excluding the architectural configuration or non-trainable buffers (unless registered explicitly). During checkpointing, we save both the model's `state_dict` and the optimizer's `state_dict` (which tracks momentum terms) to allow complete restoration of the training state.
