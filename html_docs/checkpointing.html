09. Checkpointing: Serialization & State Restoration

Why should I care?

Training runs often take days or weeks. Hardware failures, network drops, or kernel panics are inevitable during long runs. Understanding checkpoint serialization, optimizer state restoration, and device mappings is essential for saving progress and resuming training without losing work.

Level 1 — Intuition & Mental Model

Imagine you are reading a long book and need to pause. To resume reading later:

  • You save your current page number (the step index).
  • You place a bookmark in the book (the model parameters).
  • You write down a summary of the story's events in a notepad (the optimizer states).
If you forget the notepad summary, you can still read the book, but you will lose the context of the story so far. Similarly, if you load a checkpoint without the optimizer states, the model will lose its historical gradient tracking and may fail to resume training stably.

Level 2 — Engineering View

We serialize the training state using torch.save in train.py:L254-L264:

checkpoint = {
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),
    "config": config,
    "step": step,
    "val_loss": val_loss_accum
}
torch.save(checkpoint, checkpoint_path)

When loading a checkpoint, we use the saved configuration to reconstruct the model architecture before restoring the weight tensors. We must set map_location to the target hardware device to prevent cross-device load errors:

# From hellaswag.py:L168-L176
checkpoint = torch.load(args.checkpoint, map_location=device, weights_only=False)
config = checkpoint["config"]
model = GPT(config)
model.load_state_dict(checkpoint["model"])
model.to(device)

3. Mathematical View

The state dictionary maps parameter layer names to weight tensors: $$S = \{ \text{key}_i : W_i \}$$ Where $\text{key}_i$ is a string representation of the layer (e.g. "transformer.h.0.attn.c_attn.weight") and $W_i \in \mathbb{R}^{D_{out} \times D_{in}}$ is the weight tensor. When restoring a checkpoint, load_state_dict performs an element-wise copy of these tensors into the model's memory layout.

4. What happens if we do not map the device location on load?

If you call torch.load(path) without specifying map_location:

  • PyTorch will attempt to load the saved tensors directly into the memory of the device they were originally saved on (e.g. CUDA GPU 0).
  • If you run this load step on a machine without that hardware (such as your Mac Mini M4, which only has MPS and CPU), the operation will throw a runtime error (e.g. RuntimeError: Attempting to deserialize object on a CUDA device but torch.cuda.is_available() is False), crashing the program.
