10. Evaluation: Performance Validation

The Token's Journey

To confirm that our model is actually learning language patterns rather than memorizing training data, we must run validation evaluations. We feed the model unseen token text (validation split) and track the loss. We also evaluate the model on the HellaSwag benchmark, where it computes the log-likelihood (log probability sum) of four potential endings to a sentence, predicting the completion with the highest score.

flowchart TD Context["Context: 'A chef adds onions to a hot pan...'"] -->|Option 1| Opt1["'and stirs them with a wooden spoon.'"] Context -->|Option 2| Opt2["'and jumps out of the window.'"] Opt1 -->|Log-Likelihood| LL1["Score: -0.85 (High prob)"] Opt2 -->|Log-Likelihood| LL2["Score: -8.12 (Low prob)"] LL1 & LL2 -->|Compare Max| Pred["Model Prediction: Option 1 (Correct)"]

Backend Engineer Lens: Integration & Regression Testing

In backend engineering, evaluation mirrors **regression and integration validation testing**.

  • Validation Loss → Integration Test: We run validation batches without updating model weights (with torch.no_grad()). This is identical to running a unit/integration test on a staging database to verify that API response error rates are within expected SLA bounds.
  • HellaSwag Completion → Comparative Routing cost: In routing systems, we calculate path costs before choosing an execution route. In HellaSwag, we calculate the negative average log probability of the generated tokens for each of the 4 completions. We route our prediction to the option that has the lowest path cost (minimum negative log probability, representing the highest likelihood).

Production Relevance

  • LLM Benchmark Suites: Enterprise model validation goes beyond HellaSwag. Models are evaluated using automated test suites on benchmarks like MMLU (academic subject knowledge), GSM8k (multi-step math reasoning), and HumanEval (coding ability).
  • Regression Testing in Serving: When optimizing a model for production (e.g., quantizing weights from float16 to int8, compiling with TensorRT), we run evaluation benchmarks on validation sets to ensure optimization did not cause regressions in response accuracy.

Verification

We verify our model checkpoint on the HellaSwag validation subset. Run this command to load a local checkpoint and compute accuracy:

python3 hellaswag.py --checkpoint checkpoint_step_20.pt

Common Interview Followups

How does the HellaSwag benchmark evaluate an LLM? Describe the prediction math.

HellaSwag evaluates commonsense reasoning by presenting a context sentence and four possible ending options. For each ending option:

  1. We concatenate the context tokens and the ending tokens.
  2. We feed this combined sequence into the model.
  3. We extract the logits corresponding to the completion tokens.
  4. We apply a log_softmax to the logits to retrieve the log probability of each predicted token.
  5. We gather the log probabilities of the actual target completion tokens and compute their average.
The model predicts the option that yields the **highest average log-likelihood** (the smallest negative value).

Why do we slice logits starting at index `num_ctx - 1` in hellaswag.py?

In PyTorch, the outputs are shifted by 1 index because the model predicts the next token. If the context length (number of context tokens) is num_ctx:

  • The context tokens occupy indices 0 to num_ctx - 1.
  • The first completion token target is at index num_ctx.
  • The prediction (logit) for the first completion token is output by the model at the final context token position, which is index num_ctx - 1.
Therefore, to align logits with the completion targets, we slice our output logits starting at num_ctx - 1: 
logits_ending = logits[0, num_ctx - 1:]
