15. The Debugging Handbook

Why should I care?

Training and evaluating transformer models is notoriously difficult to debug. Because models fail silently (e.g. generating text but returning high perplexity, or training but converging to local minima), you must learn to read indicators like loss logs, gradient norms, and activation variance to identify and resolve bugs.

Backend Engineer Lens

Think of model debugging like tracing a distributed system failure. If an API returns a 500 error, you inspect stack traces, check database locks, and run query plans. Similarly, when a model returns NaN loss, you inspect gradient norms, trace backpropagation steps, and verify weight initialization bounds.

Troubleshooting Matrix

1. Loss Is Not Decreasing (Stagnant Training)

Symptoms: Loss remains flat around random baseline ($\approx 10.8$ for GPT-2 vocab size) and does not decrease over multiple steps.

Likely Causes:

  • Learning rate is too low.
  • Incorrect weight initialization.
  • Target index leakage or data coordinates shifted.

How to investigate: Run the --overfit batch test. If the loss does not drop close to 0 within 100 steps on a single batch, the issue is structural.

How to fix: Verify weight initializations are set to Normal(0, 0.02) and that target offset shifting is correct: y = buf[1:] and x = buf[:-1].

Real-world Frequency: Extremely common in initial setups.

2. Loss Returns NaN (Not a Number)

Symptoms: Loss values suddenly display as NaN, and training halts.

Likely Causes:

  • Gradient explosion (extremely large weight updates).
  • Division by zero in LayerNorm or attention scaling.
  • AMP FP16 mixed precision overflow.

How to investigate: Log gradient norms at each step. If the norm exceeds 10.0, the gradients are exploding.

How to fix: Enable gradient clipping (limit norm to 1.0) and verify that scaling initializations are scaled down by $1/\sqrt{2 \times \text{layers}}$.

Real-world Frequency: Common when scaling model size or batch size.

3. Generation Loops & Repetitive Outputs

Symptoms: The model generates the same phrase repeatedly during inference (e.g. "and the and the and the").

Likely Causes:

  • Greedy decoding (argmax) is used instead of multinomial sampling.
  • Temperature is set too low (e.g. $T < 0.2$).
  • Under-regularized model (missing dropout).

How to investigate: Log the selected token probabilities. If one token consistently dominates, the distribution is too narrow.

How to fix: Increase the temperature ($T \approx 0.8$) or enable top-k sampling to encourage variety.

Real-world Frequency: Common in base model inference.

4. Checkpoint Loading Failures

Symptoms: Loading a checkpoint throws shape mismatch errors or device deserialization crashes.

Likely Causes:

  • Attempting to load weights saved on a GPU directly onto a CPU or MPS device without mapping.
  • Model configuration changed since checkpoint was saved.

How to fix: Always specify the target device during load: torch.load(path, map_location=device).
