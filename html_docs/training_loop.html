07. Backpropagation: The Feedback Loop

The Token's Journey

During training, predicting the next token is only half the battle. To improve, the model needs a feedback loop to correct its parameters. Our token travels forward, producing a loss score. This loss launches a backward wave: gradients flow in reverse through all layers, computing how each weight parameter contributed to the prediction error, allowing the AdamW optimizer to update weights.

flowchart TD Inputs["Inputs [B, T]"] -->|Forward Pass| Loss["Cross Entropy Loss: Scalar"] Loss -->|Backward Pass loss.backward| Grads["Gradients computed for all layers"] Grads -->|Grad Clipping| Clip["Gradients scaled if norm > 1.0"] Clip -->|Optimizer optimizer.step| Update["AdamW adjusts model weights"]

Backend Engineer Lens: Batch Processing

In backend engineering, backpropagation acts like a **distributed transaction rollback and performance log ledger**.

  • Loss Metric → Exception Rate / SLA Drift: The loss represents how far our system deviated from the target SLA. A zero loss means the system processed the request flawlessly.
  • Gradient → Stack Trace: The gradient is a backward stack trace. It traces the exception back through all services (layers), assigning an exact coefficient of error contribution to each database table and API interface.
  • Gradient Accumulation → Batching Transactions: Running a database commit (updating weights) at every single write is slow due to transaction overhead. In GPU training, we accumulate gradients over $N$ micro-batches (writing updates to an in-memory buffer) before executing a single transaction commit (optimizer.step()). This simulates a massive batch size without running out of RAM.
  • AdamW Optimizer → Rate Limiter with Momentum: AdamW controls weight update writes, using exponential averages of past updates (momentum) to ensure the system doesn't overshoot values during correction.

Production Relevance

  • Parameter-Efficient Fine-Tuning (PEFT/LoRA): During full-parameter pre-training, we compute gradients for all 10M (or 70B) parameters. This requires keeping optimizer states for all weights, which consumes 3x more GPU memory than the weights themselves. In **LoRA**, we freeze the base model parameters (marking them read-only) and compute gradients exclusively for tiny adapter matrices, reducing optimizer RAM requirements by up to 90%.
  • Cosine LR Warmup: Learning rates are gradually scaled up (linear warmup) before decaying (cosine annealing). In production, this prevents the model from diverging on initial noisy batches, allowing stable optimization transitions.

Verification

We verify backpropagation logic by monitoring the gradient norm printed in our console. Run this command to check that the training loss decreases and gradient norms remain under control (no NaN values):

python3 train.py --steps 50

Common Interview Followups

What is the difference between standard Adam and AdamW? Why is it crucial?

In standard Adam, L2 weight regularization is added directly to the loss function. When computing the gradient of the loss, the regularization term is added to the gradient, which gets mixed with the running average (momentum) in the optimizer. This couples weight decay with learning rate updates, causing the decay rate to scale incorrectly when the learning rate changes. **AdamW** decouples this by adding the weight decay directly to the parameters at the very end of the step, after the gradient averages have been computed: $$w_{t+1} = w_t - \eta_t (\text{update}_t + \lambda w_t)$$ This ensures weights are decayed independently of learning rate changes, leading to superior model convergence.

Why do we separate parameters into decayed and non-decayed groups in train.py?

Weight decay regularizes parameters by pulling them towards zero, preventing weights from growing excessively large. We only want to apply this constraint to 2D parameters (weights in Linear and Embedding layers) because they are responsible for major projection transformations. We do not decay 1D parameters (biases and LayerNorm gains/biases) because they act as simple offsets and scaling values. Forcing biases to zero limits the model's ability to shift distributions, destabilizing normalization layers and degrading performance.

How does gradient accumulation simulate a batch size of 8,192 tokens when our hardware only supports a batch size of 1,024?

If our GPU memory is limited, loading 8,192 tokens in a single batch causes an Out-Of-Memory (OOM) error. To resolve this, we configure a micro-batch of $B=4, T=256$ (1,024 tokens). We run the forward and backward passes $N=8$ times without calling optimizer.step() or zeroing gradients. PyTorch automatically accumulates (sums) the gradients computed at each step. We divide the loss by $N$ to normalize the values. On the 8th step, we run `optimizer.step()` to update the weights. This achieves the exact same gradient update as processing 8,192 tokens in a single step, using only 1/8th of the GPU memory.
