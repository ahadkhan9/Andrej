11. The Tensor Shape Journey

The Token's Journey

We trace the exact shape dimensions of our batch as it moves step-by-step through our model configuration. Given parameters: Batch size $B=4$, Context length $T=256$, Embedding size $C=384$, Vocabulary size $V=50257$, Attention heads $H=6$, and Head dimension $D=64$ ($C = H \times D$).

Backend Engineer Lens: Shape API Contracts

In software engineering, tensor shapes act as **data model type contracts** between layers.

If you pass a list payload when an API gateway expects a map object, the validation parser throws a schema exception. Similarly, in PyTorch, layers expect precise dimension schemas. A shape mismatch error (e.g. RuntimeError: mat1 and mat2 shapes cannot be multiplied) is simply a schema validation crash. Understanding shape dimensions prevents these API contract failures.

Common Interview Followups

Why do we transpose Q, K, V from [B, T, H, D] to [B, H, T, D] before computing attention?

In PyTorch, the batch matrix multiplication operator (@ or torch.matmul) performs matrix multiplications on the **final two dimensions** of a tensor, treating all preceding dimensions as batch index dimensions. If we kept the shape as [B, T, H, D], running Q @ K.transpose(-2, -1) would try to multiply dimension $H$ by $H$, which is mathematically incorrect for our attention heads. By transposing the dimensions to [B, H, T, D]:

  • We treat both $B$ (batch) and $H$ (head count) as batch indices.
  • The final two dimensions represent sequence length $T$ and head feature dimension $D$.
  • Running Q @ K.transpose(-2, -1) computes the matrix multiplication $[T, D] \times [D, T]$ for all heads and batch elements in parallel, producing the correct score matrix of shape [B, H, T, T].

Why must we call .contiguous() before calling .view() when merging attention heads in model.py?

In PyTorch, tensors are stored in memory as contiguous blocks of bytes. Operations like .transpose() do not actually move data in memory; they simply modify the metadata stride index mapping to tell PyTorch how to read the tensor. However, the .view() method requires that the underlying data be stored contiguously in memory to compute shape changes. If you try to call .view() on a transposed tensor, it crashes with a runtime layout error. Calling .contiguous() forces PyTorch to copy the data and re-write it in memory in the new transposed order, allowing .view() to execute successfully: 

# Merging heads in model.py:
y = y.transpose(1, 2).contiguous().view(B, T, C)
