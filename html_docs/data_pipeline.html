06. DataLoaderLite: Streaming Batches

The Token's Journey

Before any training step can run, the model must receive its training data. The data loader operates behind the scenes, reading the text token stream and packaging tokens into matrices of inputs ($x$) and targets ($y$) shifted by exactly one position.

flowchart TD Corpus["Corpus Token Stream: [t0, t1, t2, t3, t4, t5]"] Corpus -->|Slice B*T+1 tokens| Buffer["Buffer: [t0, t1, t2, t3, t4]"] Buffer -->|Inputs x| Inputs["x: [t0, t1, t2, t3] (Predictive context)"] Buffer -->|Targets y| Targets["y: [t1, t2, t3, t4] (Shifted by 1 step)"]

Backend Engineer Lens: Transaction Logs

In backend engineering, the data loading pipeline is a streaming cursor reading a database transaction log.

  • Inputs & Targets → State Log Transitions: Think of the input sequence as a state transition ledger. If your input sequence $x$ is [S0, S1, S2], the targets $y$ are [S1, S2, S3]. We feed the model the state at S0 to predict S1, then S0, S1 to predict S2. It's a simple state machine transition check: current_state -> next_state.
  • Batching → Database Cursors: We don't read the entire database into memory. We use a cursor (`DataLoaderLite.current_position`) to stream chunked batches of tokens from disk, wrapping the cursor back to 0 when we reach the end of the file.

Production Relevance

  • Distributed Sharding (DDP): While our `DataLoaderLite` is a simple single-threaded loader, production training runs on thousands of GPUs. In Distributed Data Parallel (DDP) training, we shard the text corpus so that each GPU worker reads a unique chunk of data in parallel, updating weights in sync using an `AllReduce` operation.
  • Data Shuffling: In production pipelines, we shuffle data files at the start of every epoch. Shuffling breaks local document patterns, preventing the optimizer from memorizing sequential topic correlations, which would hurt general model performance.

Verification

We test our loader by printing a batch and asserting target-to-input alignment. Verify that target values at index `t` match input values at index `t+1`:

# Sanity check in Python:
from data import DataLoaderLite
loader = DataLoaderLite(B=2, T=4)
x, y = loader.next_batch()
print("Inputs: ", x[0].tolist())
print("Targets:", y[0].tolist())
# Expected: Targets should be identical to Inputs, shifted right by 1 element.

Common Interview Followups

Why do we shift target token IDs by exactly one position relative to inputs?

Because the transformer block uses a causal attention mask, each token can only attend to current and previous positions. By aligning input sequence $x = [x_0, x_1, x_2]$ with shifted targets $y = [x_1, x_2, x_3]$:

  • At index 0: the model uses $[x_0]$ to predict $x_1$.
  • At index 1: the model uses $[x_0, x_1]$ to predict $x_2$.
  • At index 2: the model uses $[x_0, x_1, x_2]$ to predict $x_3$.
This allows us to run training parallel calculations for $T$ distinct tokens in a single forward pass, rather than generating them one-by-one, maximizing GPU tensor core utilization.

What is epoch wrap-around, and why does the loader need a "+ 1" buffer margin during batch slicing?

Epoch wrap-around occurs when the streaming database cursor reaches the end of the token list. To generate a valid batch of inputs $x$ and targets $y$ of size $B \times T$, we need $B \times T$ input tokens and $B \times T$ target tokens. Since targets are shifted by 1 index, the target for the final input token requires accessing index `pos + B * T + 1`. Therefore, the loader must slice `B * T + 1` tokens from the stream. If the next slice exceeds the dataset boundary, the cursor wraps around to `0` to start a new training epoch: 

if self.current_position + B * T + 1 > len(self.tokens):
    self.current_position = 0
