16. What Interviewers Are Testing: Grilling the LLM Systems Engineer

Why should I care?

During senior and staff-level AI/ML systems and GenAI engineering interviews, interviewers test more than your ability to call APIs. They evaluate your core understanding of transformer architecture bottlenecks, memory scaling properties, optimization trade-offs, and debugging tactics. This guide presents the most common interview questions, mapping them to codebase implementations and systems answers.

1. Core Transformer Architecture Questions

Question: Write down the Multi-Head Attention formula. Explain each term and its shape.

The core self-attention formula is: $$\text{Attention}(Q, K, V) = \text{Softmax}\left( \frac{Q K^T}{\sqrt{d_k}} \right) V$$ Where:

  • $Q, K, V \in \mathbb{R}^{B \times H \times T \times D}$ representing Query, Key, and Value tensors.
  • $Q K^T \in \mathbb{R}^{B \times H \times T \times T}$ represents the similarity matrix between every token pair.
  • $\sqrt{d_k}$ is the scaling factor (where $d_k$ is the head dimension) that prevents dot products from growing too large and flattening gradients during softmax.
  • Softmax normalizes row values to sum to 1.0.
  • Multiplying by $V$ computes a weighted sum of values, returning a tensor of shape [B, H, T, D].
Code Connection: Implemented in model.py: CausalSelfAttention.forward().

Question: Why do we normalize features BEFORE sub-layers (Pre-LN) instead of AFTER sub-layers (Post-LN)?

In original transformers (Post-LN), LayerNorm was applied after residual additions: $$x_{t+1} = \text{LN}(x_t + F(x_t))$$ This caused gradients near the output layers to be massive while vanishing near input layers, requiring delicate warmups and learning rate schedules. Pre-LN (used in GPT-2 and Llama) normalizes inputs *before* they enter sub-layers: $$x_{t+1} = x_t + F(\text{LN}(x_t))$$ This creates a clean, unimpeded identity highway (residual stream) through which gradients can propagate directly during backpropagation, stabilizing training at scale. Code Connection: Implemented in model.py: Block.forward().

2. Memory & Performance Questions

Question: Audit the memory footprint required to train a 70B parameter model using AdamW in FP32 precision. What about FP16/BF16?

For a model with $N$ parameters, training memory is distributed as:

  1. Model weights: $4 \text{ bytes} \times N$ (280 GB).
  2. Gradients: $4 \text{ bytes} \times N$ (280 GB).
  3. Optimizer states (AdamW): $8 \text{ bytes} \times N$ (560 GB to store moving average of gradients and squared gradients).
This totals $16 \text{ bytes} \times N$, which is 1.12 Terabytes of static RAM (before counting dynamic activations). If we transition to **FP16/BF16 mixed precision** training:
  • Model weights and gradients are compressed to 2 bytes per parameter.
  • However, to prevent optimization drift, AdamW must maintain a master copy of weights in **FP32** (4 bytes), and its optimizer state registers remain in FP32 (8 bytes).
  • This reduces total footprint to $20 \text{ bytes} \times N$ (or $16 \text{ bytes} \times N$ with optimization), still requiring hundreds of gigabytes.
Code Connection: Audited in train.py: configure_optimizers().

Question: What is KV Cache, why do we use it in production serving, and what are its memory implications?

In autoregressive text generation, generating token $t+1$ requires attention scores computed over all past tokens $0..t$. Re-computing Queries, Keys, and Values for all past tokens at every step scales quadratically ($O(T^2)$), bottlenecking inference. **KV Cache** stores the computed Key ($K$) and Value ($V$) tensors of past tokens in GPU memory. At step $t+1$, we only compute $Q$, $K$, and $V$ for the single new token, append $K$ and $V$ to the cache, and calculate attention, reducing computational complexity to $O(T)$. Memory Implication: The cache size scales linearly with batch size, sequence length, head count, and layer depth. At scale, this consumes massive GPU RAM, limiting maximum batch sizes until optimizations like vLLM (PagedAttention) or GQA are applied. Code Connection: The generation loop without KV Cache cache-building is in model.py: GPT.generate().

3. Debugging & Optimization Questions

Question: Your training loss suddenly spikes to NaN at step 50. How do you diagnose and fix it?

A NaN loss typically indicates floating-point overflow or optimization instability:

  1. Check for Gradient Explosion: Print the gradient norm. If it is spiking, apply or tighten gradient clipping (e.g. `clip_grad_norm_(model.parameters(), 1.0)`).
  2. Audit FP16 mixed precision limits: FP16 cannot represent values above 65,504. If values exceed this, they become NaN. Switch to **BF16** (which matches FP32's exponent range) or verify that a `GradScaler` is active to scale down losses before backward passes.
  3. Reduce learning rate: A learning rate that is too high can cause parameters to step into divergent mathematical spaces, causing logits to overflow. Reduce the learning rate by a factor of 2 or 5.
Code Connection: Handled in train.py: main() gradient clipping and AMP blocks.
