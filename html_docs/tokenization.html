04. Tokenization: Byte Pair Encoding (BPE)

Why should I care?

Computers do not process words directly. How you split text into numerical tokens affects everything downstream: the model's vocabulary size, context window efficiency, parameter counts, and its ability to represent new or rare words. Understanding BPE tokenization prevents common bugs, such as character set representation errors, out-of-vocabulary crashes, or excessive parameter counts in the embedding layers.

Level 1 — Intuition & Mental Model

Imagine you have a dictionary with a limited number of pages. If you assign a unique code to every individual character, your dictionary will be very small, but writing a single sentence will require a massive string of codes. If you assign a unique code to every single word, writing a sentence will be short, but your dictionary will need millions of pages and will fail whenever you encounter a new word (like a name or slang).

Byte Pair Encoding (BPE) is the middle ground:

  • We start with a dictionary of the basic building blocks (individual bytes).
  • We scan our text and find the most common pairs of blocks (e.g. t and h) and merge them into a single new block (th).
  • We repeat this process until our dictionary reaches a target size (50,257).
This allows common words (like "the") to be represented by a single code, while rare words are broken down into smaller, recognized sub-words or characters, ensuring we can represent any text without needing an infinite dictionary.

Level 2 — Engineering View

In our data pipeline (data.py:L26-L29), we use OpenAI's tiktoken library to load the GPT-2 BPE tokenizer, convert input text to token IDs, and store them as a PyTorch tensor:

enc = tiktoken.get_encoding("gpt2")
tokens = enc.encode(text)
self.tokens = torch.tensor(tokens, dtype=torch.long)

Because the token embedding matrix (wte) and the output classification layer (lm_head) both depend on the vocabulary size ($V$), they account for a large portion of our model's parameters. To save memory, we tie the weights of these two layers in model.py:L194:

self.lm_head = nn.Linear(config.n_embd, config.vocab_size, bias=False)
self.transformer.wte.weight = self.lm_head.weight

3. Mathematical View

The token embedding lookup is a matrix multiplication: $$E = O_x \cdot W_{emb}$$ Where $O_x \in \{0, 1\}^{B \times T \times V}$ is a one-hot representation of the input tokens, and $W_{emb} \in \mathbb{R}^{V \times C}$ is the embedding matrix. In practice, PyTorch performs this lookup efficiently using index offsets rather than large matrix multiplications, but the mathematical representation remains equivalent.

4. What happens if we remove weight tying?

If we untie the weights of wte and lm_head:

  • The model's parameter footprint increases by $V \times C = 19.3\text{M}$ parameters (growing from 30M to 49M parameters).
  • During training, we must allocate additional GPU memory to store the gradients and optimizer states for this second matrix, increasing memory overhead by approximately $150\text{ MB}$.
  • Convergence will be slightly slower, as the input embeddings and output projections must learn their semantic representations independently rather than sharing updates.
