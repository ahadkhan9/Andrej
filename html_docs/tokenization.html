01. Tokenization: Payload Parsing

00. Overview → 01. BPE Parsing → 02. Embeddings → 03. Attention → 04. Pipelines → 05. Generation

The Token's Journey

Our journey begins with raw text payload: "Hello Ahad". Before entering the neural processing layers, this unstructured string must be parsed into integer primary keys. The Byte Pair Encoding (BPE) tokenizer scans the string, recognizes subword patterns, and converts the text into a sequence of two IDs: [15496, 20921].

flowchart LR Raw["String: 'Hello Ahad'"] -->|tiktoken split| Subwords["Subwords: 'Hello' + ' Ahad'"] Subwords -->|vocabulary lookup| IDs["Integer IDs: [15496, 20921]"]

Backend Engineer Lens: Payload Parsing

Think of tokenization as **payload parsing**. When client data arrives as a raw JSON string, your server doesn't execute logic on the raw string bytes. Instead, you parse it into internal data structures—mapping strings to enumerated IDs or primary keys. Similarly, a transformer cannot process raw Unicode strings. Tokenization maps unstructured text to a set of precompiled primary keys (vocabulary index 0 to 50,256) stored in a local static directory.

Transitioning to Code

Once parsed into IDs, the sequence is packed into a PyTorch LongTensor. We do not use floating-point types for tokens because they represent discrete catalog items (indexes), which will be used for matrix row lookups.

Production Relevance

  • Context Window Allocation: Because computational cost scales quadratically with sequence length, token length directly bounds your context window limits (e.g. 8k context = 8,192 token IDs).
  • RAG Text Chunking: When chunking text for retrieval, splitting by character counts can break a subword token in half (e.g. splitting "running" into "run" and "ning" across chunks). This alters their embeddings and degrades vector search relevance. Always chunk using token counts, not character counts.

Verification

We verify our tokenizer using the logit parity test and generation script. Run this command to verify that token decoding maps perfectly back to original strings:

python3 generate.py --prompt "Alan Turing determined that" --max_tokens 1

Common Interview Followups

Why do we use Byte Pair Encoding (BPE) instead of character or word tokenization?

BPE is a subword tokenization algorithm. It merges frequently occurring byte pairs. Word-level tokenization is fragile because it cannot handle new/misspelled words, and results in a massive, sparse vocabulary matrix. Character-level tokenization has a tiny vocabulary but makes sequence lengths extremely long, blowing up attention compute cost ($O(T^2)$). BPE balances this by merging common words into single tokens while decomposing rare words into character fragments, preventing out-of-vocabulary (OOV) errors.

What is the out-of-vocabulary (OOV) problem, and how does BPE solve it?

The OOV problem occurs when a model encounters a word not present in its training dictionary. BPE handles this by building its vocabulary on top of raw byte representations (values 0-255). If a word is entirely unknown, the tokenizer decomposes it down to its raw character or individual byte tokens, ensuring the model can always parse and process any input text without throwing errors.
