08. Hardware Optimization: Mixed Precision & Speedups

The Token's Journey

To train models in reasonable timeframes, we must optimize how token tensors are mapped and executed on GPU silicon. We dispatch token tensors directly to the GPU's memory buffer, scale data down from 32-bit floats to fast 16-bit registers during mathematical operations, and compile our model's Python execution graph into fast local C++ kernels.

flowchart LR FP32["FP32 Tensor: [B, T, C] (4 bytes/value)"] -->|AMP Autocast compression| FP16["FP16 Tensor: [B, T, C] (2 bytes/value)"] FP16 -->|Multiplication| GPUMatmul["GPU Matrix Core (15.2x faster)"]

Backend Engineer Lens: Compression & Compilation

In backend engineering, GPU optimization mirrors data compression and kernel compilation.

  • Mixed Precision (AMP) → Data Type Compression: Storing database entries as DOUBLE (8 bytes) when FLOAT (4 bytes) is sufficient wastes memory bandwidth and storage. Mixed precision (AMP) compresses feature weights from float32 (4 bytes) down to float16 (2 bytes) before matrix multiplication, doubling memory throughput and slashing network data transfer times.
  • torch.compile → Kernel Fusion (Stored Procedures): In typical PyTorch execution, each layer operation (e.g., adding vectors, applying GELU, LayerNorm) makes an independent call from the Python interpreter to the GPU. This is like executing 10 separate SQL queries in a loop, causing massive interpreter overhead. torch.compile fuses these steps into a single C++ execution kernel (like compiling queries into a database stored procedure), running the entire sequence on the GPU in one round-trip.
  • Device Synchronization → Thread Join Operations: PyTorch commands are asynchronous non-blocking calls. When you time a step on the CPU, the GPU might still be computing in the background. To measure step execution times accurately, we call synchronization middleware (torch.mps.synchronize() or torch.cuda.synchronize()) to halt the CPU thread until the GPU has flushed its execution buffer.

Production Relevance

  • BF16 (Brain Float 16) vs FP16: Modern enterprise training clusters (A100/H100) use BF16 instead of FP16. BF16 matches the dynamic range exponent size of FP32, preventing underflow issues during training and eliminating the need for dynamic loss scaling.
  • Triton Kernels: Serving engines like vLLM write custom GPU kernels using OpenAI's Triton language, allowing developers to write high-performance C-like GPU code in Python, bypassing standard PyTorch dispatcher limitations.

Common Interview Followups

What is the difference between FP16 and BF16? Why is BF16 preferred in modern LLM training?

Both FP16 and BF16 are 16-bit floating-point numbers, but they allocate their 16 bits differently:

  • FP16: Uses 1 sign bit, 5 exponent bits, and 10 fraction bits. The small exponent range limits its maximum value to 65,504. If gradients exceed this, they overflow to NaN. If they drop below $6 \times 10^{-5}$, they underflow to 0. This requires dynamic loss scaling to scale values up and down during training.
  • BF16 (Brain Float 16): Uses 1 sign bit, 8 exponent bits (identical to FP32), and 7 fraction bits. Because its exponent range is identical to FP32, it can represent the same range of values, preventing gradient overflow and underflow and eliminating the need for loss scaling, which stabilizes training of large models.

What is kernel fusion, and how does torch.compile implement it?

In standard PyTorch, every operation (e.g. adding residual streams and applying LayerNorm) requires reading a tensor from GPU memory, executing the mathematical operation on GPU cores, and writing the output tensor back to GPU memory. Kernel Fusion compiles these sequential operations into a single merged CUDA or Metal kernel. The GPU loads the tensor once, executes the entire chain of addition and normalization on-chip, and writes only the final result back to memory, saving significant memory-bandwidth time.
