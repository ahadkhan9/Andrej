13. Memory & Performance optimization

Why should I care?

LLM training and serving are heavily constrained by memory. If you do not understand where memory is spent, you cannot deploy models locally, write efficient fine-tuning scripts, or design serving systems that avoid out-of-memory (OOM) crashes. Managing memory parameters determines how large of a model or batch size you can support on your hardware.

Backend Engineer Lens

Think of GPU memory allocation like managing memory in a backend database cache. If you load an entire database table of 100M rows into memory (equivalent to full weights and AdamW states), you will crash the node. To scale cache performance, we index data (weight tying), compress formats (quantization), and limit temporary allocations (PEFT/LoRA).

Memory Allocations in Training

During training, memory is split into four primary categories:

1. Model Parameters (Weights)

The static weights of the model. Stored in float32: $$\text{Memory} = N \times 4\text{ bytes}$$ Where $N$ is parameter count. For our $30\text{M}$ parameter model, this takes $\approx 120\text{ MB}$.

2. Gradients

The calculated derivatives for each weight. Stored in float32: $$\text{Memory} = N \times 4\text{ bytes} \approx 120\text{ MB}$$

3. Optimizer States (AdamW)

The adaptive learning rate moment trackers. AdamW tracks two moments (mean and variance) per parameter in float32: $$\text{Memory} = N \times 8\text{ bytes} \approx 240\text{ MB}$$

4. Activations (The hidden states)

Intermediate tensor outputs generated during the forward pass must be saved in memory to compute gradients during backpropagation. This is the primary memory driver. It scales with batch size $B$, context length $T$, layer count $L$, and embedding dimension $C$. For our model: $$\text{Activation Memory} \approx B \times T \times C \times L \times 4\text{ bytes} \approx 180\text{ MB}$$

Why Inference is Cheaper

Inference (generation) requires significantly less memory than training because:

  • No backpropagation: We do not need to compute or store gradients.
  • No optimizer: We do not need to store AdamW moments.
  • No activation cache: We do not need to save intermediate states once the output token is predicted.
This reduces the memory footprint for a $30\text{M}$ model from $\approx 660\text{ MB}$ (during training) to just $\approx 120\text{ MB}$ (during inference).

PEFT, LoRA, and QLoRA

To train large models on limited hardware, we use **Parameter-Efficient Fine-Tuning (PEFT)** techniques like **LoRA (Low-Rank Adaptation)**:

  • Freezing Weights: We freeze the original model weights, meaning we do not compute gradients or store AdamW moments for them, saving significant memory.
  • Adapter weights: We inject small, trainable parameter blocks ($W_{adapter} = A \cdot B$) into attention linear layers. Only these adapter weights compute gradients and update optimizer states.
  • QLoRA: Quantizes the frozen weights to 4-bit representation (reducing weight footprint by 8x) while training 16-bit adapters, allowing large models (e.g. 8B parameters) to be fine-tuned on a single consumer GPU.
