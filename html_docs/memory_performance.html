12. Memory Audit: Where Memory Goes

The Token's Journey

When training our model, floating-point weights and activation tensors consume physical memory in our GPU's RAM. We must audit this consumption to prevent Out-Of-Memory (OOM) crashes and optimize execution throughput.

classDiagram class GPUMemory { +Model Weights (~40MB) +Gradients (~40MB) +Optimizer States (~80MB) +Forward Activations (Dynamic) }

Backend Engineer Lens: Memory Profiling

Auditing training memory is identical to **profiling a high-concurrency API server under heavy request loads**.

  • Model Weights & Gradients → Static Heap Allocation: These occupy a fixed size on the heap. Once the server boots, they remain constant, comparable to loading config caches and thread pools.
  • Optimizer States → Index Metadata Overhead: AdamW tracks historical values (mean and variance) for each parameter. This is like maintaining secondary index logs, consuming a static 8 bytes per parameter.
  • Activations → Request Stack Allocation: When a server processes an incoming request payload, it allocates transient stack memory to compute variables. If batch size $B$ or sequence length $T$ grows, activation memory scales linearly, representing transient request thread buffers. High concurrency (large batch sizes) will blow up activation memory, causing OOM crashes.

Peak Training Memory Breakdown

For a model with $N$ parameters, trained using **AdamW** in **FP32** precision, memory is distributed as follows:

Category Formula RAM for 10M Model RAM for 70B Model RAM Behavior
Model Parameters $4 \text{ bytes} \times N$ ~40 MB 280 GB Static
Gradients $4 \text{ bytes} \times N$ ~40 MB 280 GB Static
Optimizer States (AdamW) $8 \text{ bytes} \times N$ ~80 MB 560 GB Static
Activations Scales with $B \times T \times L \times C$ Dynamic (~120 MB) Dynamic (Terabytes) Scales linearly with batch size

Production Relevance

  • Activation Checkpointing: To save memory during deep model training, we use activation checkpointing. Instead of saving all activation vectors during the forward pass (which consumes massive memory), we discard them. During the backward pass, we re-compute them on-the-fly by running the forward pass for that block again. This reduces peak activation memory usage by 70% at the cost of a ~30% computation time overhead.
  • Quantization (INT8 / INT4): When serving a model in production, we do not compute gradients or track optimizer states. Weights can be quantized from float16 down to int4 (using engines like GPTQ or AWQ) to compress weight size, allowing a 70B parameter model (~140GB in FP16) to fit onto a single 80GB A100 GPU.

Verification

We audit parameters using the optimizer configuration step in `train.py`. The ~10M model correctly reports ~10.4 Million learnable parameters, taking up less than 200MB of static training RAM on our local Mac Mini M4, well within the 16GB system limit.

Common Interview Followups

Why does training a model require significantly more GPU memory than running inference on the same model?

In inference, we only need to load the model parameters into GPU RAM, and we do not calculate gradients or track optimizer metrics. The only dynamic memory consumer is the KV Cache, which is minor. In training, we require:

  1. Model weights (4 bytes per parameter).
  2. Gradients (4 bytes per parameter).
  3. Optimizer states (8 bytes per parameter for AdamW to store moving averages of gradients).
  4. Activations: We must keep every block's forward activation tensor in memory because they are required to compute derivatives during the backward pass.
Thus, training a 70B model requires over 1.1 Terabytes of GPU memory, whereas inference only requires ~140 GB.

What is Activation Checkpointing, and what engineering trade-off does it present?

Activation Checkpointing is a memory optimization technique that trades compute cycles for RAM. During the standard forward pass, the model caches activations for all layers in memory so the backward pass can use them to compute gradients. With activation checkpointing:

  • We only save activations at the boundaries of major segments (e.g. at the input of every 4th transformer block).
  • All intermediate block activations are discarded from memory.
  • During the backward pass, we re-run the forward pass locally starting from the nearest saved boundary checkpoint to re-generate the discarded activations.
This reduces peak memory usage from $O(\text{layers})$ to $O(\sqrt{\text{layers}})$, allowing much larger batch sizes at the expense of a 30-33% increase in total training step time due to redundant forward computations.
